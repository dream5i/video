## 1. 这份文档解决什么问题

前面我们已经有一批企业级治理文档。

但企业项目真正难的，不是“有没有文档”，而是：

`到底哪些现在必须补，哪些可以后补，哪些暂时不要补。`

小白版解释：

- 不是把所有看起来高级的东西都一口气加上
- 而是先补会影响开发、并行、验收、上线的关键缺口

## 2. 先给主控结论

当前判断：

- 文档和规则层面对齐度：`约 75% - 80%`
- 平台执行和工程落地对齐度：`约 50% - 60%`

这不是精算分数，而是主控判断。

它的意思是：

- 我们已经不缺“方向类文档”
- 也不缺“第一版规则”
- 真正缺的是把规则变成平台门禁、执行证据和演练记录

一句话版本：

`现在要补的不是更多概念，而是更强的执行闭环。`

## 3. 当前分级原则

为了后面不跑偏，统一按 3 个级别处理。

### 3.1 必补

定义：

- 不补会直接影响并行开发、正式验收、发布准备或企业级可控性

### 3.2 可后补

定义：

- 重要，但不补不会立刻卡住当前主链推进

### 3.3 暂不补

定义：

- 现在补了看起来高级
- 但会明显增加管理成本，收益不够

小白版解释：

- `必补` 是地基上的承重墙
- `可后补` 是后面逐步装上的系统柜
- `暂不补` 是现在先别买的豪华装修

## 4. 必补项

下面这些，是我建议当前阶段必须补齐的 6 项。

| 项目 | 当前状态 | 为什么现在必须补 | 补到什么程度才算过线 |
| --- | --- | --- | --- |
| GitHub 平台强制门禁 | 已落地第一版单人阶段安全版 | 这是把规则从“写在文档里”推进到“平台真拦得住” | `main` 禁直推、required checks 真正生效；多人协作时再升级到 required review 和 code owner review |
| ADR 真实决策记录 | 已补首批关键 ADR | 后续边界变化仍然会发生，必须防止重新回到口头决策 | 当前第一批 ADR 已覆盖主链范围、分层异步架构、provider 策略和主控治理；后续继续按变化增补 |
| 版本门槛证据总表 | 分散在多份文档里 | 企业验收看的是“证据链”，不是口头判断 | 有一份可追踪清单，能链接到测试结果、配置、截图、日志或审批结论 |
| 可观测性平台接线 | 字段和日志已落第一版 | 没有 dashboard / alerting，出问题还是靠人工翻日志 | 至少有主链健康看板、基础错误告警、request/trace 可定位 |
| 恢复与事故演练 | 文档已写，未演练 | 企业最怕“文档写得会，真出事不会” | 至少做 1 次 backup/restore 演练和 1 次 incident drill，并留记录 |
| AI 结果验收底线 | 测试策略里有方向，未收口 | 这个项目是 AI 编程和 AI 产出驱动，不能只验代码不验结果 | 先定义最小 AI 输出验收标准，至少覆盖分析结果、workflow 草稿、render 结果 |

### 4.1 必补项排序

我建议按下面顺序补：

1. GitHub 平台强制门禁
2. ADR 真实记录
3. 版本门槛证据总表
4. 可观测性平台接线
5. 恢复与事故演练
6. AI 结果验收底线

原因很简单：

- 前 3 项是“先把制度和证据链装上”
- 后 3 项是“再把运行保障和 AI 质量底线装上”

进度更新：

- `2026-04-25` 已完成第 `1` 项的第一版落地
- `2026-04-25` 已完成第 `2` 项的第一批基线落地，新增 4 条关键 ADR
- `2026-04-25` 已完成第 `3` 项的第一版落地，新增 [version-gate-evidence-ledger.md](./version-gate-evidence-ledger.md)
- 当前下一项主控优先级已切到第 `4` 项：可观测性平台接线

## 5. 可后补项

下面这些很重要，但不建议现在停下主链开发专门去补满。

| 项目 | 当前状态 | 为什么可以后补 | 建议触发时机 |
| --- | --- | --- | --- |
| 完整性能压测体系 | 还没系统化 | 当前还在骨架和主链稳定期，过早压测收益有限 | 接近 staging 前 |
| 更细的成本预算和 error budget | 已有 NFR 第一版 | 真实 provider 和真实流量还不够稳定 | provider 接入稳定后 |
| 更完整的安全自动化扫描矩阵 | 已有 dependency gate 第一版 | 先把关键门禁和边界守住更重要 | 仓库规则稳定后 |
| 多浏览器、多分辨率 E2E 套件 | 已有 1 条主链 E2E | 先保证主链和异常场景，再扩覆盖面 | 第二轮页面回归时 |
| 组织级角色拆分 | 当前单主控模型 | 现在人还没扩到那一步，先把制度定好即可 | 多人协作正式开始时 |
| 对外 SLA / SLO 包装 | 只有工程底线 | 现在更像内部搭建期，不是正式对外服务期 | 准备外部上线前 |

## 6. 暂不补项

下面这些，当前阶段我建议明确“不急着补”。

| 项目 | 为什么现在不补 |
| --- | --- |
| 很重的微服务拆分治理包 | 当前主链和团队规模还不需要，会明显增加复杂度 |
| 完整企业合规文档套件 | 现在还没有进入正式外部交付和法务合规阶段 |
| 过细的多级审批链 | 当前还是单主控 + 项目 owner 模式，过早上复杂审批只会拖慢 |
| 大而全的 AI 评测平台 | 先定义最小 AI 验收底线，比先搭大平台更实用 |
| 复杂的多环境发布编排 | 在 staging / production 真实落地前，先不要假装全都已经有了 |

小白版解释：

- 这些不是永远不要
- 而是现在做，成本大于收益

## 7. 现在和大厂标准还差在哪里

压成一句最实在的话：

`我们现在已经有“大厂会写出来的规则框架”，但还缺“大厂会真正装到系统里、跑过演练、留过证据”的那一半。`

具体差距主要在 4 类：

### 7.1 从文档到平台

- 规则已经写了
- 但平台还没强制拦住

例子：

- `CODEOWNERS` 已有
- 但 GitHub ruleset / branch protection 还没完全生效

### 7.2 从原则到证据

- 我们已经会说“可以开发”“还不能上线”
- 但还缺一张统一证据表来证明为什么

### 7.3 从预案到演练

- 恢复、回滚、事故处理文档已有
- 但还缺真实演练记录

### 7.4 从代码验收到 AI 结果验收

- 代码测试已经开始成型
- 但 AI 结果质量的验收底线还没真正固定

## 8. 主控建议的补齐节奏

我建议后面按 3 个小阶段推进。

### 阶段 A：先补制度闭环

目标：

- 让规则真的能卡住风险改动

动作：

- 打开 GitHub 平台门禁
- 补关键 ADR
- 建版本门槛证据总表

### 阶段 B：再补运行闭环

目标：

- 让问题发生后能看见、能处理、能恢复

动作：

- 接 dashboard / alerting
- 做 backup/restore 演练
- 做 incident drill

### 阶段 C：最后补 AI 质量闭环

目标：

- 让 AI 项目的验收不只看“代码能跑”

动作：

- 定最小 AI 输出验收标准
- 补第一版 AI eval 样本和回归入口

## 9. 当前是否需要继续补文档

我的判断是：

`需要补，但只补会直接驱动执行的文档。`

具体说：

- 可以继续补：
  - 能直接指导平台配置
  - 能直接指导验收
  - 能直接指导演练
  - 能直接指导 AI 结果判定
- 不建议继续补：
  - 重复性的分析文档
  - 只讲概念、不落动作的说明文
  - 现在没人会执行的重型治理文档

## 10. 一句话结论

现在我们和大厂企业级项目标准化流程的差距，不在“有没有框架”，而在：

`有没有把框架变成平台门禁、执行证据、真实演练和 AI 结果验收标准。`

所以接下来的正确动作不是“继续堆文档”，而是：

`补关键闭环，再继续开发。`
