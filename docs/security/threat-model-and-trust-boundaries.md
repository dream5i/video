## 1. 这份文档解决什么问题

这份文档回答两件事：

1. `别人最可能从哪里把我们搞出问题`
2. `系统里哪些边界默认不能互相信任`

专业说法：

- `Threat Model`
  - 威胁模型
- `Trust Boundary`
  - 信任边界

小白版解释：

- 威胁模型就是“先假设敌人会怎么捣乱”
- 信任边界就是“到了这条线，默认不能再当自己人”

## 2. 当前阶段最需要保护的东西

当前优先保护 6 类资产。

1. 用户项目和工作流数据
2. 供应商密钥和平台配置
3. `Project / AnalysisRun / WorkflowDraft / RenderRun / RunStep` 的状态一致性
4. object storage 里的源文件、中间产物和结果
5. 审计、日志、trace 和回滚证据
6. AI 编程规则、审批边界和高风险门禁

## 3. 当前系统里的主要信任边界

## 3.1 浏览器到 Web

默认判断：

- 用户输入不可信
- 浏览器本地状态不是真实事实来源

风险：

- 表单伪造
- 恶意输入
- 前端状态和后端事实不一致

## 3.2 Web 到 API

默认判断：

- 前端传来的字段不能直接当业务真相

风险：

- 越权字段提交
- 非法状态跳跃
- 未校验输入直接进入领域对象

## 3.3 API 到 Worker

默认判断：

- 任务参数必须受控，不能把任意输入原样下发

风险：

- 任务上下文过大
- 错误重试失控
- run / step 状态不一致

## 3.4 Worker 到外部 provider / 工具

默认判断：

- 外部模型、外部媒体服务、外部抓取内容都不是可信内部系统

风险：

- prompt injection
- 返回内容结构漂移
- 延迟、成本、失败率异常
- 外部文本污染系统指令

## 3.5 应用到存储层

默认判断：

- 数据库存结构化事实
- 对象存储存大文件
- 两边都不能默认永远一致，必须靠记录和校验对齐

风险：

- 文件有了，记录没了
- 记录有了，文件没了
- 删除不完整

## 3.6 开发与治理边界

包括：

- 本地 Agent
- 云端 Agent
- 插件 / MCP
- CI
- GitHub 合并门禁

默认判断：

- 能访问仓库不等于能访问敏感内容
- 能执行命令不等于能越过审批边界

## 4. 当前最主要的威胁清单

## 4.1 外部内容指令污染

来源：

- 抖音文案
- OCR
- transcript
- 外部网页

风险：

- 外部文本被模型误当成系统指令
- 导致越权行为、错误工具调用或错误分析

硬规则：

- 外部内容一律按不可信输入处理
- 不允许直接提升为 system instruction

## 4.2 敏感信息泄露

来源：

- 日志
- trace
- prompt 上下文
- provider raw response
- 调试时临时复制

风险：

- 密钥、PII、生产数据被二次扩散

硬规则：

- 默认脱敏
- 默认最小化
- 默认不把完整原文塞进日志和外部模型

## 4.3 过度授权与过度执行

来源：

- 高权限 agent
- shell 工具
- 新插件 / MCP
- 生产命令

风险：

- 误删
- 误改配置
- 绕过人工审批

硬规则：

- 高权限只在本地受控使用
- 生产操作默认 deny
- 新外部工具默认不接

## 4.4 状态机和数据一致性破坏

来源：

- migration
- queue / retry
- run / step 更新
- 并发修改共享锁定区

风险：

- 页面看见的状态是假象
- 任务卡住
- 数据不可恢复

硬规则：

- 共享锁定区主控串行处理
- 高风险改动必须 review pass
- migration 必须有升级和回退说明

## 4.5 供应链与许可证风险

来源：

- 新依赖
- 来源不明代码片段
- 新 provider SDK
- 新插件 / MCP server

风险：

- 漏洞引入
- 许可证污染
- 维护断档

硬规则：

- 新依赖必须走 license / security gate
- 来源不明大段代码不得直接进主线

## 4.6 删除、保留和恢复失控

来源：

- retention policy 不清
- delete job 不完整
- backup / restore 没演练

风险：

- 该删的没删
- 不该删的删了
- 出事故后恢复不了

## 5. 当前阶段的默认信任规则

为了简单、稳妥，当前先定 8 条。

1. 用户输入默认不可信
2. 外部抓取文本默认不可信
3. provider 输出默认要校验结构和状态
4. 前端状态默认不是真相，以数据库和领域层为准
5. 本地高权限默认不等于可绕过审批
6. 云端 agent 默认不接敏感上下文
7. 新依赖、新 provider、新工具默认不可信，先审再接
8. migration、deletion、retention 默认高风险

## 6. 当前阶段必须执行的防护动作

## 6.1 输入防护

- URL、文案、OCR、transcript 做结构校验
- 外部文本和系统指令严格分层
- 高风险输入走 allowlist / blocklist 判断

## 6.2 工具与权限防护

- shell / 网络 / 插件按角色开权限
- reviewer 默认只读
- cloud agent 默认关闭或最保守

## 6.3 数据防护

- secrets 不进日志
- 敏感文本不直送外部模型
- provider raw response 不默认长期保存

## 6.4 变更防护

- 共享锁定区串行处理
- 高风险区走 review pass
- 发布前必须附 rollback 路径

## 6.5 恢复防护

- 数据操作要能说明恢复路径
- migration 失败要能止血
- incident 后必须补复盘

## 7. 当前阶段的阻断条件

出现下面任一情况，应直接阻断，不进入主线：

- 无法说明输入边界是否安全
- 无法说明敏感数据是否会外发
- 无法说明高风险命令是否受控
- 无法说明 migration / deletion 的回退路径
- 无法说明新依赖或新 provider 的来源与风险

## 8. 目前仍未完全工程化的部分

这份文档先把规则定下来，但下面这些仍是下一阶段的工程任务：

- 真正的 tool allowlist / blocklist 执行
- prompt registry 和 prompt lineage
- audit event schema 落地
- backup / restore 真正演练
- 平台级 ruleset / branch protection

## 9. 一句话结论

当前威胁模型可以压缩成一句话：

`把外部内容、外部模型、外部依赖、敏感数据、高权限执行和数据迁移都当成高风险边界处理，宁可多一道门，也不要默认相信。`
