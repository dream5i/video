## 1. 这份文档解决什么问题

这份文档回答的是：

`一个新依赖或一段外部代码，到底能不能进主线。`

小白版解释：

- 不是“能跑就装”
- 而是先看安不安全、能不能维护、会不会有版权麻烦

## 2. 当前总原则

1. 能不用新依赖，就先不用
2. 新依赖必须说明为什么现有方案不够
3. 来源不明的大段代码不能直接进主线
4. 许可证不清楚，默认不进
5. 安全风险不清楚，默认不进

## 3. 适用范围

这份门禁适用于：

- npm / pnpm 新包
- Python 新包
- 第三方 SDK
- 新 provider client
- GitHub 上拷来的代码片段
- MCP server / plugin / external tool

## 4. 进入主线前必须回答的 6 个问题

1. 这个东西是从哪里来的？
2. 为什么必须引入，而不是直接用现有能力？
3. 最近还有没有维护？
4. 许可证能不能接受？
5. 会不会触碰安全、数据、网络、执行权限边界？
6. 如果将来要移除，成本大不大？

只要有一项说不清，就不要直接进入主线。

## 5. 当前许可证策略

## 5.1 默认可接受

在没有额外限制时，当前优先接受：

- MIT
- Apache-2.0
- BSD-2-Clause
- BSD-3-Clause
- ISC

## 5.2 需要单独评估

默认不自动放行，必须单独说明边界和影响：

- MPL
- LGPL
- SSPL
- 商业双许可证

## 5.3 当前默认阻断

以下情况默认不进入核心主线：

- GPL
- AGPL
- 未注明许可证
- 无法确认来源的大段代码

小白版解释：

- 不是说这些一定“违法”
- 而是对当前项目来说，先不要把后续法律和分发风险带进核心仓库

## 6. 依赖风险分级

## 6.1 低风险

特点：

- 许可证清楚
- 社区活跃
- 只在前端样式或开发工具层使用
- 不触碰安全、网络、执行权限

处理：

- 可走普通 review

## 6.2 中风险

特点：

- 接入构建链
- 接入数据库或网络
- 进入 Worker 或 provider path

处理：

- 主控审查
- 说明用途和替代方案

## 6.3 高风险

特点：

- 能执行命令
- 能访问网络
- 能读写文件
- 能影响 auth / migration / provider / CI
- 许可证存在争议

处理：

- 高风险 review pass
- 人工批准
- 必要时安全复核

## 7. 当前推荐的审查清单

每次新增依赖，至少附这 7 项：

1. 包名 / 版本
2. 官方来源链接
3. 许可证
4. 维护状态
5. 用在什么路径
6. 不引入它会怎样
7. 回退方案

## 8. 外部代码片段规则

当前硬规则：

1. 不直接粘贴来源不明的大段代码
2. 参考开源项目结构可以，但不要直接混入核心逻辑
3. 如有明确参考来源，应在 PR 或文档中写出
4. 遇到 public-code 高相似内容，应人工判断是否需要替换

## 9. MCP / Plugin / External Tool 的额外门禁

因为这类东西不只是代码，还可能带执行能力，所以额外检查：

- 是否需要网络访问
- 是否会读取敏感文件
- 是否能执行 shell
- 是否会扩大 AI agent 的行动面

默认策略：

- 未登记的一律不接
- 接入前必须说明权限边界和回退方式

## 10. 当前阶段的执行方式

当前还没有把所有门禁都平台化，但至少先按下面流程执行。

1. 提交引入理由
2. 主控做初审
3. 如触碰高风险边界，进入 review pass
4. 发布前在 release checklist 里再次确认

## 11. 下一阶段建议平台化的门禁

后续应逐步做成可执行门禁：

- GitHub dependency review
- 锁文件变更审查
- license scan
- 安全漏洞扫描
- SBOM 产出

小白版解释：

- 现在先靠制度和审查
- 后面再把制度变成自动拦截

## 12. 一句话结论

当前依赖和许可证门禁的核心原则是：

`不清楚来源的不进，不清楚许可证的不进，会扩大权限面或供应链风险的先审后进。`
