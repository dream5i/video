## 1. 一句话定义

`全新项目` 是一个面向电商短视频场景的 AI 工作台：用户输入一条爆款短视频链接或手动补充商品信息，系统自动完成内容拆解、卖点提炼、脚本与镜头方案生成，并进入一个预填充的可编辑工作流，最终产出一版视频初稿或可执行的生成包。

## 2. 这版 PRD 要解决什么

这份文档不是最终商业计划书，而是为了让我们能尽快回答下面几个执行层问题：

1. 首版产品到底解决哪个最小但真实的问题。
2. 哪些功能属于 `MVP 必做`，哪些必须后置。
3. 用户从进入系统到拿到结果的主流程是什么。
4. 产品结构和技术结构应该如何拆，才能尽快开工。

## 3. 产品假设

### 3.1 核心假设

在电商短视频场景里，用户最痛的不是“完全不会生成视频”，而是：

- 看到了一个爆款，但不会快速拆成可复用结构。
- 能想到卖点，但不会整理成可执行脚本和镜头。
- 想快速出第一版视频方案，但又不想一上来面对复杂剪辑和空白画布。

所以首版产品最应该解决的是：

`让用户在 5 分钟内，从一个爆款链接或商品描述，拿到一份可编辑、可执行的短视频制作方案，并尽可能生成第一版结果。`

### 3.2 产品价值主张

与“纯视频生成器”相比，`全新项目` 的核心价值不是模型数量，而是流程组织能力：

- 用强入口拿到真实需求
- 用分析能力建立信任
- 用预填充工作流减少操作负担
- 用结构化结果提高复用率

## 4. 目标用户

### 4.1 核心用户

#### 用户 A：电商内容运营

- 日常需要高频做商品短视频
- 会找爆款参考，但缺少系统拆解方法
- 需要快速出多个方案给老板或团队看

#### 用户 B：短视频投手 / 操盘手

- 关注点击率、转化率、前 3 秒 hook、卖点节奏
- 更在意“为什么这个内容有效”以及“怎么快速做变体”

#### 用户 C：小团队创始人或主理人

- 没有成熟内容团队
- 想从竞品或爆款里快速提炼表达方式
- 更需要“一步一步带着走”的工具，而不是专业编辑器

### 4.2 暂不优先的用户

- 专业影视后期团队
- 需要复杂时间线编辑的高级视频制作人
- 首要目标是长视频生产的内容机构

## 5. JTBD

### 5.1 主要任务

当我看到一条适合我产品的爆款短视频时，我希望系统能帮我快速拆出它的结构、卖点和台词逻辑，并给我一套能直接改、能直接做的生成方案，这样我不用从空白开始。

### 5.2 次要任务

当我只有商品信息但没有参考视频时，我希望系统能根据卖点自动生成一套脚本和镜头框架，帮我快速开始。

### 5.3 用户当前痛点

- 爆款分析靠手工，慢而且主观
- 视频制作流程割裂，脚本、镜头、素材和生成工具不在一个地方
- 工具太强大时，新手反而更容易卡住
- 生成结果经常是黑盒，用户不知道中间怎么来的

## 6. 产品原则

### 6.1 强入口优先

首版必须让用户能用最自然的方式进入系统，优先支持：

- `爆款短视频链接`
- `手动输入商品信息`

### 6.2 默认不是空白

首版不让用户从空白节点画布开始，而是先进入：

- 已经生成好的脚本骨架
- 已经填好的镜头卡片
- 已经配置好的默认流程

### 6.3 中间过程可见

分析结果、脚本、镜头方案、风格设定都必须可编辑，不能只给一个黑盒最终结果。

### 6.4 稳定优先于炫技

首版宁可只接一个稳定的生成链路，也不追求同时支持很多模型和供应商。

### 6.5 资产可以复用

每次分析和生成都应该沉淀为：

- 项目
- 结果
- 脚本
- 模板
- 历史记录

## 7. MVP 产品范围

### 7.1 MVP 目标

MVP 的目标不是做一个完整平台，而是验证下面这个最短闭环：

`爆款链接输入 / 商品信息输入 -> 内容分析 -> 脚本与镜头方案 -> 预填充工作流 -> 生成结果页`

### 7.2 MVP 输出承诺

首版至少要保证输出下面两类结果：

#### 必须产出

- 结构化分析结果
- 可编辑脚本
- 可编辑镜头方案
- 可再次打开的项目页

#### 尽量产出

- 一版 9:16 短视频初稿
  或
- 一份可交给生成引擎执行的结构化生成包

说明：

如果视频成片链路在实现阶段复杂度过高，`MVP` 也可以先以“生成包 + 项目回放”形式上线，但产品文案不能夸大为完整成片平台。

### 7.3 MVP 必做功能

#### P0-1. 新建项目入口

- 支持输入一条短视频分享链接
- 支持手动输入商品名称、目标人群、卖点补充
- 支持选择目标比例，首版先支持 `9:16`

#### P0-2. 链接解析与基础抽取

- 识别来源平台
- 拉取视频资源或必要元数据
- 保存源链接与解析状态
- 失败时给出明确错误提示

#### P0-3. 内容分析

- 音频转写
- 画面 OCR / 文字提取
- 卖点提炼
- 结构拆解
- Hook / 节奏 / CTA 段落识别
- 生成简洁分析报告

#### P0-4. 脚本与镜头方案生成

- 输出可编辑的脚本草稿
- 输出镜头清单或镜头卡片
- 给出推荐风格和节奏说明
- 支持手动修改每一段内容

#### P0-5. 预填充工作流

- 将分析结果自动转成项目工作流
- 工作流 UI 首版采用“步骤卡片 / Storyboard”形态
- 每一步都有默认值，不出现空白画布

#### P0-6. 生成运行

- 用户点击后创建一次生成任务
- 首版只接 1 条稳定的生成路径
- 展示运行状态：排队、处理中、成功、失败
- 失败可重试，且要有失败原因

#### P0-7. 结果页与历史

- 查看本次项目的分析、脚本、镜头方案和生成结果
- 支持再次编辑并重新运行
- 历史页可查看最近项目

### 7.4 MVP 应该后置的功能

#### P1

- 商品 URL 自动抓取
- 案例库
- 模板库
- 多变体批量生成
- 多语言本地化
- 简单积分或额度体系

#### P2

- 角色库 / AI Actor
- 高级可视化节点编辑器
- 团队协作
- API / 开放平台
- 自动发布到社交平台

### 7.5 MVP 明确不做

- 全功能时间线编辑器
- 大而全的模型广场
- 用户自配秘钥 `BYOK`
- 复杂权限系统
- 多组织协作和审批流

## 8. 核心用户流程

### 8.1 主流程 A：爆款链接模式

1. 用户输入一条爆款短视频链接
2. 系统完成解析、转写、OCR 和结构分析
3. 系统输出分析摘要、脚本草稿和镜头方案
4. 用户在预填充工作流里修改卖点、风格和镜头
5. 用户点击生成
6. 系统运行任务并产出结果页
7. 用户保存、复看或再次生成

### 8.2 主流程 B：商品信息模式

1. 用户输入商品名称、目标人群、核心卖点
2. 系统直接生成脚本骨架与镜头方案
3. 用户编辑并启动生成
4. 结果进入项目页和历史页

### 8.3 关键体验要求

- 从输入到看到结构化分析结果，时间尽量控制在 `90 秒内`
- 从输入到拿到可编辑工作流，尽量控制在 `3 分钟内`
- 任何失败都必须能告诉用户“失败在哪一步”

## 10. 功能需求明细

### 10.1 新建项目

#### 功能要求

- 支持粘贴链接
- 支持校验输入是否合法
- 支持手动输入商品信息
- 支持项目标题自动生成

#### 成功标准

- 用户无需额外学习就能知道如何开始

### 10.2 分析引擎

#### 输入

- 视频链接
- 视频文件
- 手动商品信息

#### 输出

- transcript
- OCR 文本
- 卖点列表
- 结构段落
- 脚本草稿
- 镜头建议

#### 成功标准

- 输出结果足够结构化，可直接驱动后续工作流

### 10.3 预填充工作流

#### 功能要求

- 工作流不是空白
- 每个步骤都可编辑
- 有默认风格值
- 支持保存草稿

#### 成功标准

- 用户第一次进入也知道下一步要做什么

### 10.4 生成任务

#### 功能要求

- 可创建 run
- 可跟踪状态
- 可显示失败原因
- 支持重新运行

#### 成功标准

- 用户不会在“到底有没有在跑”这件事上产生不确定

### 10.5 结果与历史

#### 功能要求

- 项目可以回看
- 结果可以再次编辑
- 历史按最近更新排序

#### 成功标准

- 产品不是一次性体验，而是持续可复用

## 12. 成功指标

### 12.1 北极星指标

- 用户是否能在一次会话内，从输入走到“得到结构化方案或初版结果”

### 12.2 MVP 核心指标

- 新建项目成功率
- 链接解析成功率
- 分析成功率
- 从分析页进入工作流页的转化率
- 从工作流点击生成的转化率
- 首次结果产出时长
- 生成任务成功率
- 历史复访率

### 12.3 体验指标

- 失败任务是否有明确错误原因
- 用户是否会反复回到首页重新新建
- 用户是否会修改脚本和镜头，而不是直接放弃

## 13. 风险与应对

### 13.1 风险一：外部供应商不稳定

#### 风险

- 视频解析失败
- 分析模型失败
- 成片生成失败

#### 应对

- 每一步状态单独记录
- 错误原因单独展示
- 保留中间产物，失败后不必全链路重跑

### 13.2 风险二：首版范围失控

#### 风险

- 同时做链接解析、商品抓取、角色库、案例库、批量生成，范围会过大

#### 应对

- 首版只做 `爆款链接 + 手动商品信息 + 预填充工作流 + 结果页`

### 13.3 风险三：工作流太复杂

#### 风险

- 用户又会掉进空白和复杂配置

#### 应对

- 首版只做 Storyboard 式工作流，不做高级节点图

### 13.4 风险四：产品承诺过度

#### 风险

- 如果成片链路还不稳定，但文案宣传成“自动出片”，会损伤信任

#### 应对

- 上线时按真实能力定义文案
- 如果必要，先把“结果”定义为生成包和项目方案，而不是完整成片

## 14. 建议的开发阶段

### 14.1 Phase 0：产品与技术验证

- 确认 1 条稳定的视频解析链路
- 确认 1 条稳定的分析链路
- 确认 1 条稳定的生成链路
- 产出最小交互原型

### 14.2 Phase 1：输入与分析

- 新建项目页
- 链接解析
- 手动商品信息输入
- 分析结果页

### 14.3 Phase 2：工作流与结果

- 预填充工作流页
- 项目保存
- 历史页
- 结果页

### 14.4 Phase 3：生成任务与稳定性

- 后台 run
- 重试机制
- 错误提示
- 状态追踪

### 14.5 Phase 4：MVP 后增强

- 案例库
- 模板库
- 商品 URL 抓取
- 多变体生成

## 15. 推荐的技术方向

首版技术结构建议遵循“前端体验清晰，后端编排稳定”的原则。

### 15.1 前端

- `Next.js` 或 `React + Vite`
- 重点是项目流转、状态展示、可编辑卡片式工作流

### 15.2 后端

- `FastAPI` 更适合首版
- 原因：
  - 更适合对接转写、OCR、视频处理、AI 调用
  - 更适合快速串起分析与生成任务

### 15.3 后台任务

- 独立 job queue
- 每一步单独记状态
- 支持 retry 和 fallback

### 15.4 媒体与 AI 能力

- link parser
- transcript / OCR
- script planner
- shot planner
- provider adapter
- renderer / compositor

## 16. 当前结论

`全新项目` 的正确起点不是“做一个大而全的视频平台”，而是：

`先做出一条从爆款链接到可执行短视频方案的最短主链路。`

只要这条链路跑顺，后面再叠加模板、案例、角色、批量化和 API，都会更自然。
