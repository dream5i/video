## 1. 这份文档解决什么问题

这份文档回答的是：

`这个系统至少要稳到什么程度、快到什么程度、能扛到什么程度，才算没有失控。`

专业说法：

- `NFR`
  - Non-Functional Requirements
  - 非功能需求
- `SLO`
  - Service Level Objective
  - 服务目标

小白版解释：

- 功能需求回答“做什么”
- 非功能需求回答“做得有多稳、多快、多省、多容易恢复”

## 2. 当前适用范围

这份基线适用于：

- 当前内部搭建阶段
- 可控并行阶段
- 进入 external beta 前的工程门槛设计

当前明确不是：

- 对外商业 SLA 承诺

小白版解释：

- 这是一份“工程底线”
- 不是“对客户签字保证书”

## 3. 当前阶段最重要的 5 条底线

1. 主链不能经常断
2. 页面上的关键操作不能明显卡死
3. 长任务必须有状态，不允许黑盒卡住
4. 问题出现后要能被发现，而不是靠人猜
5. 成本和重试不能无限放大

## 4. 服务分级

为了不把所有东西都混成一个指标，当前把系统分成 3 类。

### 4.1 A 类：同步用户操作

例如：

- 新建项目
- 读取项目页
- 保存工作流草稿
- 查询 run 状态

### 4.2 B 类：异步后台任务

例如：

- 分析
- 预填 workflow
- 生成
- 重试

### 4.3 C 类：平台与工程保障

例如：

- CI
- migration
- 队列
- 存储
- 回滚

## 5. 当前阶段的最小 SLO

## 5.1 同步用户操作

| 项目 | 当前基线 |
| --- | --- |
| 新建项目 / 读取项目 / 保存草稿等普通同步接口成功率 | `>= 99.0%` 在受控环境中 |
| 普通同步接口 `p95` 响应时间 | `<= 1.5s` |
| 启动长任务的提交接口 `p95` 响应时间 | `<= 3s` |
| 页面看到最新 run 状态的刷新延迟 | `<= 10s` |

小白版解释：

- 用户点完按钮后，应该很快收到“已经开始处理”或“保存成功”
- 不能让用户怀疑按钮没点上

## 5.2 异步后台任务

| 项目 | 当前基线 |
| --- | --- |
| 分析 / 生成任务必须落 run 和 step 状态 | `100%` |
| 任务运行中必须有最近心跳或步骤更新时间 | `100%` |
| 同一任务无限重试 | `禁止` |
| 单次失败后的自动重试上限 | `<= 3 次`，超过后转人工判断 |
| 失败后必须给出错误分类 | `100%` |

小白版解释：

- 后台慢一点可以接受
- 但“完全不知道它是不是死了”不可以接受

## 5.3 工程与发布保障

| 项目 | 当前基线 |
| --- | --- |
| 合并主线前统一验证 | `pnpm verify` 必须通过 |
| 高风险改动 | 必须有 review pass |
| migration 改动 | 必须有升级路径和回滚说明 |
| 上线准备前 | 必须满足 release checklist |

## 6. 当前阶段的容量基线

专业说法：

- `Capacity Baseline`

小白版解释：

- 就是先定“这版系统先按多大体量设计”

当前先按受控内部试运行规模设计：

- 日新增项目：`100` 以内
- 同时活跃 run：`10` 以内
- 单个项目的自动 fan-out：`默认禁止无限扩散`
- 单次任务自动重试：`最多 3 次`

注意：

- 这不是市场承诺
- 这是当前工程设计的安全起点

如果后面准备扩大流量，这份文档要先升级。

## 7. 当前阶段的可用性判断

当前不承诺正式对外 SLA，但对内部工程质量，至少要求：

- 主链演示环境在活跃开发时段尽量可用
- 如果主链关键成功率明显下降，优先止血，不继续加功能

当前的 feature freeze 触发条件建议为：

1. 最近 `20` 次主链人工或自动验证里，成功率低于 `90%`
2. 同步接口 5xx 明显升高且持续 `30` 分钟以上
3. 高风险回归影响主链，且 `4` 小时内还未止血

一旦触发：

- 暂停继续扩功能
- 主控转入修复和稳定性收口

## 8. 成本与重试底线

当前阶段先定 4 条硬规则：

1. 每次模型调用都应记录 provider、model、latency、retry、cost 估算
2. 不允许无上限自动重试
3. 不允许未经批准的一次任务多供应商并行乱试
4. provider 异常率明显升高时，应优先降级或暂停，而不是盲目加压

小白版解释：

- 不是“调用失败了就一直再试”
- 不然很容易把钱烧出去，还把系统拖死

## 9. 数据一致性底线

当前阶段至少保证下面这些不乱：

1. `Project`、`AnalysisRun`、`WorkflowDraft`、`RenderRun`、`RunStep` 的状态要能对上
2. 页面展示的主状态不能和数据库事实长期不一致
3. migration 不能没有升级路径和回退说明
4. 结果文件和结构化记录要能互相对应

## 10. 可恢复性底线

当前阶段先给出工程底线，不给出最终生产承诺。

至少要求：

- 主线回滚路径要存在
- migration 要写 downgrade 或替代修复方案
- 重大故障后要能定位是哪次改动引发

正式的 `RTO / RPO` 会在数据治理与恢复文档里再定版。

小白版解释：

- 现在先保证“出事能退”
- 再逐步升级成“多久恢复、最多丢多少数据”这种更严格的承诺

## 11. 升级为外部 beta 前必须补齐的指标

在真正准备对外开放前，至少要把下面这些从“方向”升级成“可测量”：

1. 主链成功率
2. 分析链路 `p95` / `p99`
3. 生成链路耗时分布
4. 队列积压时间
5. provider 错误率
6. 每 run 成本
7. 错误预算

## 12. 当前阶段的工程结论

这份基线的核心不是把数字写得很夸张，而是先把下面这件事定住：

`宁可先定一个保守但可执行的底线，也不要没有底线地一边扩功能一边碰运气。`
