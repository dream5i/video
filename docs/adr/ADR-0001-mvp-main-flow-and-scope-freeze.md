# ADR-0001：冻结 MVP 主链与范围边界

状态：Accepted
日期：2026-04-25

## 标题

当前阶段只围绕一条 MVP 主链施工：

`输入 -> 分析 -> 预填充工作流 -> 运行 -> 结果 -> 历史`

## 背景

当前项目要做的是电商短视频场景的 AI 工作台。

最容易失控的地方，不是“不会写代码”，而是：

- 一边搭一边加需求
- 看到竞品什么都有，就忍不住都想加
- 页面、数据模型和 provider 结构还没稳，就先扩成大平台

如果范围不先冻结，后面会出现三个问题：

- 主链不断改口
- contract 和 schema 跟着漂
- 每一轮开发都像在重新定义产品

## 决策

我们正式决定：

- 当前只做一条 MVP 主链：`输入 -> 分析 -> 预填充工作流 -> 运行 -> 结果 -> 历史`
- 所有页面、API、Worker 和测试，优先围绕这条主链补齐
- 会改变主链、导航、核心对象或非做不可范围的新增项，必须先补 ADR

当前明确不做：

- 空白节点工作流画布
- BYOK
- 公开 API
- 团队协作
- 多组织权限
- 全时间线视频编辑器
- 模型市场
- Harness 进入核心产品运行路径

当前允许讨论但不能默认顺手做进去的扩展项：

- 商品 URL 抓取
- 多语言
- 多变体批量生成
- 第二种 render 路径
- 角色库 / 案例库

## 备选方案

1. 一开始就按“大而全平台”开工

优点：

- 看起来一步到位
- 未来功能点预留很多

缺点：

- 主线容易失焦
- 数据模型和页面结构会反复返工
- 对当前单主控搭建阶段不友好

为什么没有采用：

- 当前目标是先把最短可用主链打稳，不是一次做成完整平台

2. 先只做宣传页或 Demo 壳

优点：

- 上手快
- 页面更容易先出效果

缺点：

- 不能形成真正可持续的主链
- 对 API、Worker、数据和治理帮助有限

为什么没有采用：

- 我们要的不是一个展示页，而是一个可以持续长大的工作台骨架

## 影响

产品影响：

- 后续需求判断有统一尺子
- 先把“能用的一条链”做实，而不是四处开口

架构影响：

- Web / API / Worker / Data 的设计都围绕单主链收口
- 主流程相关对象可以继续冻结而不频繁改名

数据 / contract 影响：

- `Project`、`AnalysisRun`、`WorkflowDraft`、`RenderRun`、`RunStep` 继续作为当前核心对象
- 任何会扩大这些对象职责的改动，都需要先评估再落地

开发流程影响：

- 后续排期和并行拆分，优先服务主链，不先扩外围大功能

## 实施与回滚

实施方式：

- 继续以 `product-mvp-prd.md`、`main-flow-diagram.md`、`implementation-roadmap.md` 为施工主线
- 新增功能评估时，先判断是否改变本 ADR 的边界

需要同步的文档：

- `docs/product-mvp-prd.md`
- `docs/main-flow-diagram.md`
- `docs/implementation-roadmap.md`
- `docs/index.md`

回滚条件：

- 如果后续出现明确业务证据，证明当前单主链无法支撑最小用户价值
- 或者多个必须能力被反复挡在范围外，导致架构持续绕路

回滚方式：

- 先补新的范围 ADR
- 再统一更新 PRD、路线图和相关 contract 文档
