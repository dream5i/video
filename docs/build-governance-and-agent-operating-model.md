## 1. 这份文档要解决的问题

这份文档不是讲产品功能，而是讲之后真正开始搭项目时，如何保证：

- 一直沿着同一条主线推进
- 项目边界不随实现过程漂移
- 多 Agent 协作时不互相打架
- 工作树和代码审查有治理
- 我在整个过程中的角色清楚，不会时而统筹、时而乱写、时而没人审

## 2. 先给结论

如果先用一句话概括，我建议采用：

`单主控、强边界、有限委派、主控集成、主控终审、高风险二次审查`

拆开讲就是：

1. 我作为主控统筹，负责架构、拆任务、集成、最终评审。
2. 默认情况下，我同时承担实现和审查责任，但高风险改动要加一轮独立复查。
3. 子 Agent 只用于边界清晰、写入范围互不重叠的任务。
4. 关键合同层和共享核心层，原则上由主控亲自改，或至少主控串行整合。
5. 所有偏离既定边界的新增功能，必须先通过决策记录，不允许边写边扩 scope。

## 3. 什么还需要补充，才能让后续搭建不跑偏

目前我们已经有：

- 竞品分析
- 竞品扩展地图
- MVP PRD
- 信息架构
- 技术架构
- 边界与复用策略
- AI 编程栈建议

为了真正能“沿一条线走”，我建议再补 4 个执行型约束件。

### 3.1 根目录执行规则文件

文件建议：

- `AGENTS.md`

作用：

- 给未来每次进入项目的 AI 说明最短主链路、冻结边界、禁止事项、协作规则
- 作为比长文档更短、更像“施工红线”的东西

### 3.2 ADR 目录

目录建议：

- `docs/adr/`

作用：

- 所有会影响边界和架构的大变化都要写 ADR
- 例如：是否加入商品 URL 抓取、是否引入第二种 render 路径、是否改工作流表示层

### 3.3 实施路线图

文件建议：

- `docs/implementation-roadmap.md`

作用：

- 把“文档已确定的范围”翻译成阶段任务
- 明确 P0 先做什么，哪些文件夹先建，哪些接口先定

### 3.4 合同冻结清单

文件建议：

- `docs/schema-and-contract-freeze.md`

作用：

- 把最不该乱改的结构先冻结出来
- 包括：
  - `StoryboardDraft`
  - `Project / AnalysisRun / RenderRun / RunStep`
  - provider interfaces
  - 状态枚举

如果这些不先冻结，后面实现很容易左右漂移。

## 4. 项目边界怎么规定死

这里我建议直接分成 3 类：

### 4.1 已冻结的 MVP 主链路

当前只能围绕这条主链路搭：

`输入 -> 分析 -> 预填充工作流 -> 运行 -> 结果 -> 历史`

这条主链路里的关键对象已经明确：

- Project
- SourceAsset
- AnalysisRun
- WorkflowDraft
- RenderRun
- OutputAsset
- RunStep

### 4.2 已冻结的不做事项

以下内容在没有单独决策之前，视为明确不做：

- 空白节点工作流画布
- 大而全模型广场
- 用户 BYOK
- 团队协作
- 公开 API
- 多组织权限
- 全时间线视频编辑器
- Harness 进入核心运行路径

### 4.3 允许扩展，但必须走决策流程的事项

这些不是永远不做，但不能默认顺手做进去：

- 商品 URL 抓取
- 多语言
- 多变体批量生成
- 第二种 render 路径
- 角色库
- 案例库
- Anthropic secondary provider 接入
- ComfyUI sidecar

规则：

- 只要新增内容会影响主链路、数据模型、UI 导航或 provider 结构，就必须先写 ADR 或至少先改决策文档。

## 5. 我在后续搭建中的角色怎么定

这个问题我建议明确，不要模糊。

### 5.1 我的默认角色

我默认是：

- 主控统筹
- 架构守门人
- 集成者
- 最终代码审查者

这意味着：

- 我负责任务切分
- 我决定哪些部分可以并行
- 我对最终进入主线的代码负责
- 我要保证代码、文档、边界一致

### 5.2 我是不是也做实现

是。

默认情况下，我不是只做 PM 或 reviewer，我也会直接写代码。

但我的实现方式应该是：

- 关键核心层，我亲自写或亲自改
- 可并行、边界清晰的功能层，交给子 Agent 实现
- 我负责收口、审查和集成

所以不是“我只统筹不写”，也不是“我什么都自己写不分派”，而是：

`主控亲自做核心，委派做边缘，最后统一收口。`

### 5.3 我是不是默认兼任代码审查

是，默认兼任。

但我要再加一个更稳的规则：

- 所有改动，我自己都要做自审
- 高风险改动，要额外加一轮独立复查

换句话说：

- 日常改动：我实现 + 我自审
- 高风险改动：我实现或整合 + 额外 review pass

## 6. 子 Agent 怎么用

### 6.1 什么时候应该派子 Agent

只有满足下面条件时才应该派：

1. 任务边界清晰
2. 写入范围明确
3. 与我手头的关键路径不冲突
4. 我能给出明确验收标准

适合派子 Agent 的任务：

- 独立页面 UI 实现
- 测试补齐
- 某个 adapter 的独立实现
- 单独的 schema 或类型整理
- 某一块文档化和只读探索

补充一条当前已确认的执行授权：

- 进入并行开发时，主控可以主动安排子 Agent，不需要每次先停下来再次征求是否允许分派
- 但前提不变：边界清晰、写入范围独立、验收标准明确

### 6.2 什么时候不应该派

以下情况原则上不派，或者只派探索型 Agent，不派写代码的 Agent：

- 核心架构刚刚变化
- 共享 schema 还没冻结
- 多个模块同时依赖同一文件集
- 数据库模型正在定
- provider 接口正在定
- 我下一步动作直接依赖这部分结论

也就是说，下面这些区域默认由主控亲自做：

- `packages/contracts/**`
- `services/api/app/domain/**`
- `services/api/app/providers/interfaces/**`
- 数据库 migration
- 根配置

### 6.3 子 Agent 的职责定位

子 Agent 不是平行架构师，而是：

- bounded implementer
- read-only explorer
- targeted reviewer

它们不拥有最终产品方向。

最终方向、整合、取舍，由主控负责。

### 6.4 子 Agent 任务单必须包含什么

以后如果我派子 Agent，每次任务单都应该至少写清楚：

- 任务目标
- 允许编辑的文件范围
- 禁止编辑的文件范围
- 验收标准
- 测试要求
- 与其他 Agent 不要互相覆盖的提醒

如果没有这些，子 Agent 很容易把 scope 扩散。

## 7. 要不要派“代码守卫”Agent

这个问题我建议不要机械化处理。

### 7.1 默认策略

默认不在每一次编辑前都派“代码守卫”。

原因：

- 会拖慢速度
- 很多小改动不值得增加一道并行角色
- 过度治理会让 MVP 阶段失去推进效率

### 7.2 推荐策略

推荐采用：

- `主控自审 + 高风险改动额外 review pass`

如果已经进入并行 lane，再补一条默认链路：

- `实现子 Agent 完成 -> reviewer 子 Agent 查一轮 -> 主控终审和集成`

也就是：

- 普通 UI、小型文档、小范围非核心逻辑：我自己实现后自己审查
- 并行任务：实现 Agent 先交付，reviewer Agent 先查，再由我做最后审查和收口
- 高风险区域：实现后再加一个 reviewer agent 做第二轮检查

另外，为了避免我在长周期开发里逐渐从“主控”滑成“局部实现者”，再加一个固定锚点：

- 当项目 owner 说 `回主控` 时，我先重读 [main-controller-reanchor-prompt.md](./main-controller-reanchor-prompt.md)
- 先回到主控视角，再判断是否继续写代码、是否拆任务、是否补 review pass

### 7.3 哪些改动必须触发额外 review pass

以下改动建议强制触发独立复查：

- 数据库 schema
- migration
- provider interface
- adapter contract
- auth / user / billing
- 文件删除逻辑
- 队列和重试机制
- 状态机
- 根配置

### 7.4 review pass 应该查什么

review agent 的任务重点不是重写代码，而是查：

- 是否越界改动
- 是否破坏既定 schema
- 是否引入状态不一致
- 是否测试覆盖不足
- 是否偏离主链路

## 8. 工作树治理怎么做

目前这个目录还不是 git 仓库，但一旦正式开工，我建议第一步就进入工作树治理。

### 8.1 基础规则

- 先初始化 git
- `main` 只用于稳定集成
- 每个并行任务单独分支
- 每个并行 Agent 单独 worktree
- 一个 worktree 只做一类任务

### 8.2 worktree 目录建议

建议结构：

```text
全新项目/
├── .worktrees/
│   ├── web-home/
│   ├── api-contracts/
│   ├── worker-analysis/
│   └── review-pass/
```

说明：

- 主工作区用于统筹、文档、集成和最终收口
- 子 Agent 不在主工作区直接乱改

### 8.3 分支命名建议

- `feat/web-home`
- `feat/api-contracts`
- `feat/worker-analysis`
- `fix/run-status`
- `review/schema-pass`

### 8.4 文件所有权规则

同一时间只能有一个写作者拥有某个核心文件集合。

建议先把下面这些视为“共享锁定区”：

- `packages/contracts/**`
- `services/api/app/domain/**`
- `services/api/app/providers/interfaces/**`
- `services/api/alembic/**`
- 根目录配置文件

这些区域如果要改：

- 要么由主控亲自改
- 要么串行修改，不并行

### 8.5 合并规则

建议规则：

- 子 Agent 不直接最终合并
- 主控审查后再集成
- 如有冲突，主控负责解决
- 合并前至少跑对应测试

## 9. 实施阶段的推荐工作模式

### 9.1 阶段一：单线程定骨架

这个阶段不适合大量分派。

建议主控亲自完成：

- 仓库结构
- 根配置
- 合同层
- 数据模型
- provider interface

原因：

- 这些一旦分散改，很容易一开始就失控

### 9.2 阶段二：可控并行

等骨架稳定后，再并行做：

- web 页面
- API 读接口
- worker 独立步骤
- 测试补齐

这个阶段适合派子 Agent。

### 9.3 阶段三：收口与稳态

接近可运行时，重点回到主控：

- 集成
- 状态统一
- review pass
- 文档回填
- 缺陷修补

## 10. Definition of Done

为了避免“写完但没真正落地”，每个任务我建议都满足下面这组 done 标准：

- 没有越界改动
- 和现有文档一致
- 对应测试已补齐或说明未补齐原因
- 关键路径可运行
- 状态与错误处理完整
- 必要文档已更新
- 如果触碰共享合同层，已做 review pass

## 11. 我建议现在马上补上的两样东西

如果你同意，我建议下一步不是直接乱开工，而是先补这两个执行件：

1. `AGENTS.md`
   用非常短的规则把项目红线写死
2. `docs/implementation-roadmap.md`
   把第一阶段要做的仓库骨架、contract、provider interface 拆成明确任务

## 12. 最终结论

如果你要我把这件事压成最直接的执行原则，就是：

- 我做主控统筹，也做核心实现，也做最终审查
- 子 Agent 只做边界清楚、写入范围独立的任务
- 不默认给每次改动都派代码守卫
- 但高风险改动必须加一轮 review pass
- 骨架阶段优先单线程
- 稳定后才并行
- worktree 必须一任务一树，一树一负责人
- 所有边界变化先过决策，再进实现
