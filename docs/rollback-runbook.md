## 1. 这份文档解决什么问题

当一次改动引发：

- 主链中断
- 状态不一致
- 运行失败率异常
- 数据结构错误

不应该现场拍脑袋。

这份 Runbook 的目标是：

`先止血，再回滚，再复盘。`

## 2. 回滚触发条件

以下任一情况出现时，应进入回滚判断：

- 核心页面无法打开
- 主链关键接口异常
- 新 migration 造成数据写入失败
- run 状态机出现明显不一致
- 成本、重试、失败率异常放大

## 3. 回滚顺序

### 3.1 先止血

优先动作：

- 暂停继续合并
- 暂停可疑任务入口
- 暂停可疑队列或步骤

### 3.2 再回滚代码

优先回退最近一批明确可定位的变更。

要求：

- 主控负责收口
- 高风险改动回滚仍需人工确认

### 3.3 最后处理数据

如果涉及 schema / migration：

- 先判断是否可以安全 downgrade
- 不能安全 downgrade 时，走人工修复或前滚修复
- 不允许在数据影响不明时直接操作

## 4. 最低记录要求

每次回滚至少记录：

- 哪次变更引发问题
- 影响范围
- 先止了什么血
- 用了哪条回滚路径
- 还有哪些残留风险

## 5. 当前阶段建议的回滚路径

### A. 页面或 contract 级问题

- 回退到上一版稳定提交
- 重新运行 `pnpm verify`
- 再决定是否重新进入主线

### B. API / 状态机问题

- 先切断新入口
- 回退最近状态逻辑改动
- 校验关键项目状态是否仍一致

### C. migration 问题

- 先停止继续升级
- 优先走明确定义过的 downgrade
- 无安全 downgrade 时，人工批准后走修复脚本或前滚

## 6. 回滚后的复盘问题

- 哪个检查没拦住
- 哪个证据包缺失
- 哪个 review pass 应该更早触发
- 是否需要补测试、规则或 ADR
