## 1. 这份文档解决什么问题

这份文档回答的是：

`系统真出事时，谁来接、怎么分级、什么时候该升级、什么时候该回滚。`

小白版解释：

- 不是出事了大家一起慌
- 而是先按级别分清楚“谁主带、谁批准、谁同步、先做什么”

## 2. 当前阶段的默认角色

因为项目还不是完整团队，所以当前默认角色是：

- `Incident Commander`
  - Main Controller
- `Business Approver`
  - Project Owner
- `Recorder`
  - Main Controller 兼任，后续可拆

## 3. 事故分级

当前先分 4 级。

### 3.1 Sev 1

定义：

- 主链完全不可用
- staging / production 关键环境不可用
- migration 造成大面积写入失败
- 敏感数据疑似泄露

动作：

- 立即止血
- 立即升级给 Project Owner
- 立即评估回滚

### 3.2 Sev 2

定义：

- 主链部分可用但失败率明显升高
- 生成、分析、历史等关键功能大面积异常
- provider 故障导致核心链路持续失败

动作：

- 快速定位
- 必要时暂停发布或暂停合并
- 视情况回滚或降级

### 3.3 Sev 3

定义：

- 非核心功能异常
- 局部性能明显下降
- 少量用户受影响

动作：

- 排入快速修复
- 按版本节奏收口

### 3.4 Sev 4

定义：

- 低风险缺陷
- 文案、样式、小范围体验问题

动作：

- 正常排期

## 4. 当前阶段的响应顺序

统一使用下面 5 步。

1. `Declare`
   - 明确这是不是事故
2. `Stabilize`
   - 先止血
3. `Diagnose`
   - 找根因和影响面
4. `Recover`
   - 回滚、降级或修复
5. `Review`
   - 复盘并补规则

## 5. 当前阶段的止血优先级

出事故后，先做下面这些，而不是先争论根因。

1. 暂停继续合并
2. 暂停可疑入口
3. 暂停可疑队列或步骤
4. 判断是否立即回滚
5. 同步当前影响面

## 6. 升级矩阵

| 情况 | 默认级别 | 必须通知谁 | 是否暂停合并 | 是否优先评估回滚 |
| --- | --- | --- | --- | --- |
| 主链完全不可用 | `Sev 1` | Main Controller + Project Owner | 是 | 是 |
| migration 失败 | `Sev 1` | Main Controller + Project Owner | 是 | 是 |
| 敏感数据疑似泄露 | `Sev 1` | Main Controller + Project Owner | 是 | 是 |
| 分析或生成失败率显著升高 | `Sev 2` | Main Controller | 是 | 是 |
| 非核心功能异常 | `Sev 3` | Main Controller | 否 | 否 |
| 轻微体验问题 | `Sev 4` | Main Controller | 否 | 否 |

## 7. 当前阶段的同步节奏

### Sev 1

- 首次判断后尽快同步
- 恢复前持续同步关键进展

### Sev 2

- 在影响确认后同步一次
- 重要转折再同步

### Sev 3 / 4

- 按正常修复节奏记录

## 8. 什么时候必须回滚优先

下面这些情况，默认优先评估回滚，而不是继续在线硬修：

- 主链完全中断
- migration 已破坏写入
- 高风险改动刚发布且问题明确
- 成本、重试、失败率迅速放大

## 9. 当前阶段的事故记录最低要求

每次事故至少记录：

- 发现时间
- 影响范围
- 分级
- 负责人
- 先做了哪些止血动作
- 最终如何恢复
- 是否触发回滚
- 需要补什么规则或测试

## 10. 复盘必须回答的 5 个问题

1. 这次为什么没提前拦住？
2. 哪个门禁本来该拦但没拦住？
3. 哪个告警本来该响但没响？
4. 哪个回滚动作不够快？
5. 后续是补测试、补规则，还是补平台门禁？

## 11. 当前阶段的阻断条件

如果发生下面任一情况，在复盘和止血完成前，不继续扩功能：

- `Sev 1`
- 连续出现主链失败
- 数据一致性问题未收口
- 无法确认是否有敏感数据影响

## 12. 一句话结论

当前事故响应模型的核心原则是：

`先分级、先止血、再恢复、最后复盘，严重事故先保主链和数据，再谈功能进度。`
